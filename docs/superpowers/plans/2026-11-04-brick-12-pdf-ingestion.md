# Brick 12: Reading a PDF with Exact Page Anchors Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Read a text-based PDF into evidence-ready records, each with the page, the printed page label, the exact words, and a box on the page, so every finding can point at the real spot and a later brick (ADR-004) can draw red-ink marks exactly there. Code, not the AI, proves an anchor is real.

**Architecture:** New folder `packages/domain/src/ingest/`. `preflight` decides if a file may be read at all (spec section 8). `extract` turns a PDF into pages of text spans with boxes. `anchors` finds exact text and builds `Anchor` records, and verifies any anchor (including one an AI proposed) against the extracted page. `checkAnchors` reports anchors that do not match their page. Synthetic PDFs only, generated by the tests.

**Tech Stack:** TypeScript, vitest. New dependencies, vetted in Task 1: `pdfjs-dist` (reading; Apache-2.0, Mozilla, released 2026-11-01) and `pdf-lib` as a dev-only fixture writer (MIT; no release since 2022, so never used in shipped code).

**Spec:** `docs/spec/MASTER_SPEC.md` sections 8, 9, 15, 22; `docs/decisions/ADR-004-red-ink-markup-output.md`; `Anchor` and `Document` in the contract.

## Global Constraints

- Synthetic PDFs only. No real report, no customer data, no network. Nothing is uploaded anywhere.
- Never run anything inside a PDF. Scripts, actions, and embedded files are ignored and flagged.
- Reject without reading: wrong file type by content (not by file name), encrypted, over the size or page limits, ZIP or macro or executable. Limits come from a config file (`data/rules/limits.json`), labeled as proposed targets (D06); no limit is hard-coded in logic.
- Exact text is stored exactly as extracted; a normalized copy is stored separately. Page index (1-based) and printed page label are kept separately (spec 8).
- An anchor that cannot be verified is never drawn on, never trusted, and never repaired by guessing.
- Boxes are normalized 0 to 1 with the origin at the top left of the page as displayed (after page rotation).
- Scanned pages are marked unreadable for text (no OCR in this brick). A document with some of them is `partially_readable`, never silently complete.
- Real customer files must be parsed in an isolated worker with resource limits (spec 8). This brick parses in-process for tests only; the isolated worker is recorded as a blocker for any real upload (roadmap phase 6).
- Types check and all tests pass before each next task. Commit after each task.

## Review Focus

- A file named `report.pdf` that is really a ZIP, an executable, or plain text: rejected by content.
- Encrypted, truncated, and zero-page PDFs: a clear reason, no crash, nothing partly read.
- Page rotation (90, 180, 270): boxes still land on the displayed words.
- The same phrase on several pages or twice on one page: `multiple_matches` is flagged and the caller must choose; never silently the first.
- A phrase broken across two lines or hyphenated at a line end: found, flagged `split_across_lines`, box covers both lines.
- Ligatures and curly quotes: exact text kept as extracted; matching uses the normalized copy; the anchor stores the exact one.
- A verified anchor whose words were changed by one character, or moved to another page: fails verification.
- A page with no text layer: no spans, flag `no_text_layer`, document `partially_readable`.
- Page-count limit checked from the file structure before any text work.
- Known gap, recorded not fixed here: invisible (white or tiny) text hidden in a PDF to steer an AI. Add detection in a later brick; until then all extracted text is treated as untrusted data (Brick 11).
